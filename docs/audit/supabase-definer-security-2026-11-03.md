# تدقيق دوال SECURITY DEFINER — موقع 967

**التاريخ:** 3 نوفمبر 2026  
**المصدر:** تعريفات PostgreSQL الحية، فاحص Security Advisors، سياسات RLS، مراجع كود `AihamAnter/967-initiative`، وإرشادات Supabase.  
**المشروع:** Supabase الخاص بموقع 967. لم تُستخدم أو تُنسخ مفاتيح أو كلمات مرور.

## النتيجة بالأرقام

| المعيار | قبل الإصلاح | بعد الإصلاح |
|---|---:|---:|
| دوال SECURITY DEFINER المتاحة للزائر `anon` | 14 | **11** |
| دوال SECURITY DEFINER المتاحة للمستخدم المسجل `authenticated` | 42 | **38** |
| إجمالي تنبيهات هاتين الفئتين | 56 | **49** |
| دوال `public` المختلفة المكشوفة | 42 | **38** |

> التنبيه من هذا النوع يعني أن الوظيفة قابلة للاستدعاء بصلاحيات مالكها، **ولا يثبت** أن الاستدعاء يتجاوز فحوص الصلاحيات أو يكشف بيانات. تقارن الأدوات وجود المنفذ لا كيفية استخدامه بالكامل.

## منهج التدقيق

1. جرد الدوال ذات `prosecdef=true` والاستدعاء بـ `anon` أو `authenticated` من `pg_proc` و`has_function_privilege`، مع قراءة تعريفات الدوال.
2. جميع الدوال الـ42 التي ظهرت في الجرد الأولي كانت مملوكة للدور `postgres`، وتستخدم `SET search_path TO ''`.
3. مطابقة استعمال الدوال داخل سياسات `pg_policies` والدوال المساعدة الأخرى، والبحث عن أسمائها في المستودع.
4. مراجعة مسارات الحماية عند تعديل المناظرات، وبيانات الدليل، والتحرير المباشر، ومركز المهام. معظم الكتابة المحمية تعتمد على `auth.uid()` أو `debate_role()` أو `task_role()` أو `editorial_can_read()` أو `directory_assert_writer()`.
5. مراجعة حقول `debates` و`debate_speakers` ودوال القراءة العامة: عرض المناظرات المشورة مرتبط بحالة النشر، وحقول المتحدثين المنشورة لا تتضمن عمود بريد خاص في مخطط الجدول الذي فُحص.
6. المحافظة على أي دالة يستخدمها الموقع مباشرة أو يعتمد عليها RLS، بدل سحب الصلاحيات بالجملة.

## الإصلاح الأول: صلاحية التحرير قبل قفل المناظرة

ترحيل Supabase: `20261103001023_harden_debate_admin_authorization_before_lock`.

في `public.debate_admin_mutate(text,uuid,bigint,jsonb)` كان فرع `save` يقفل سجل المناظرة ويستخرج بيانات العناصر المرتبطة به قبل أن يصل الاستدعاء إلى دالة التعديل القديمة التي تفحص صلاحية المحرر.

أُضيف في بداية الدالة:
```sql
if public.debate_role() is null then
  raise exception 'Editor required' using errcode='42501';
end if;
```

الفحص يعتمد على صلاحية المحرر المؤكد وغير المحظور. **لم تتغير** طريقة التعديل، وتحقق النسخة، وسجلات النشاط، وتوقيع RPC أو منح `EXECUTE` السابقة. أصبح رفض الاستدعاء غير المصرح به يسبق عمليات القفل والقراءة.

ملف المستودع: `supabase/migrations/20261103001023_harden_debate_admin_authorization_before_lock.sql`.

## الإصلاح الثاني: منع الاستدعاء المباشر لأربع دوال داخلية

ترحيل Supabase: `20261103001314_restrict_backend_only_definer_helpers`.

أُزيل `EXECUTE` من `PUBLIC` و`anon` و`authenticated` عن:

| الدالة | سبب تقييدها |
|---|---|
| `debate_live_results_visible(uuid)` | فحص داخلي تستخدمه دوال `SECURITY DEFINER`، وليس واجهة المستخدم مباشرة |
| `debate_participation_state(uuid)` | مُساعِد داخلي تستدعيه `debate_live_results` |
| `debate_visible(uuid)` | مُساعِد داخلي تستدعيه دوال المناظرة بصلاحية مالكها، ولا تستعمله سياسة RLS مباشرة |
| `is_967_editor()` | دالة تحقق قديمة؛ لم تُرصد لها استدعاءات موقع مباشرة أو مراجع في سياسات RLS الحالية |

احتفظ `postgres` و`service_role` بإمكانية التنفيذ. ولا تزال الدوال المنشورة `debate_catalog` و`debate_detail` و`debate_discussion` و`debate_live_results` تعمل دون تغيير.

ملف المستودع: `supabase/migrations/20261103001314_restrict_backend_only_definer_helpers.sql`.

## الدوال التي تُركت متاحة عمدًا

- **القراءة العامة:** مثل `debate_catalog` و`debate_detail` و`debate_speaker_public` و`debate_discussion`؛ تستخدم حالة النشر أو مسارًا مقيدًا للمناقشات.
- **مساعدات سياسات RLS:** مثل `is_editor` و`is_management` و`is_ranking_editor` و`editorial_can_read` و`debate_role` و`task_role` و`task_visible` و`task_can_edit`؛ إزالة `EXECUTE` منها قد تتسبب في رفض الاستعلامات الصحيحة.
- **أوامر التحرير للمستخدمين المسجلين:** وظائف حفظ الأدلة والتعديلات، وإدارة الرسائل والمهام والمناظرات؛ الاستدعاء متاح لمستخدمي `authenticated` لكنّ التعديل يتطلب فحصًا داخليًا للدور والصلاحية، وليس مجرد تسجيل الدخول.
- **الصيانة:** `task_archive_completed` تستدعيها واجهة المهام الإدارية عند القراءة، وقد تُستدعى من Cron؛ سحب `EXECUTE` عنها يكسر سلوك الأرشفة الحالي. تفويضها الخاص يستحق مراجعة منفصلة إذا تغيرت أدوار العاملين.

## الاختبارات التي نفذت على قاعدة البيانات

- تطبيق الترحيلين بنجاح والتحقق من تسجيلهما في سجل Supabase.
- التحقق من وجود فحص `debate_role()` قبل قفل السجلات، وبقاء الدالة `SECURITY DEFINER` مع `search_path` مُحدد.
- تأكيد زوال صلاحية `EXECUTE` للأدوار العامة عن الأربع دوال، وبقاء `service_role` مخوّلاً.
- اختبار داخل معاملة `READ ONLY` بدور `anon`: فهرس المناظرات ما زال يعيد JSON، و`is_editor()` لا يمنح صلاحية محرر دون جلسة، والدوال الداخلية الأربع غير متاحة.
- اختبار داخل معاملة `READ ONLY` بدور `authenticated` **دون JWT صالح**: القراءة العامة تعمل، ومسارات عرض المناظرات المبنية فوق الدوال الداخلية تعمل، ومحاولة `debate_admin_mutate('save',...)` تفشل بالرمز `42501`. جرى `ROLLBACK` ولم تتغير بيانات الموقع.

مراجعة الاختبار داخل المستودع: `tests/supabase-definer-security-20261103.test.mjs`، ونسخة SQL القابلة للتشغيل: `scripts/sql/verify-security-definer-rpc-20261103.sql`.

## المتبقي والتحذيرات

بقي **11 تنبيهًا للزوار و38 للمسجلين**، وهي قائمة تتضمن عمليات قراءة عامة ومساعدات RLS وأوامر أُبقيت لأنها تحتاج `SECURITY DEFINER`. لا يجب إسكات التنبيهات بسحب جميع الصلاحيات.

ما لم يُختبر في هذه المهمة:
- تنفيذ حفظ فعلي بحساب محرر مخوّل داخل واجهة الإنتاج، لأنه قد يعدّل المحتوى.
- فحص اختراق شامل لكل تفرع استثنائي في كل دالة، أو تدقيق رموز جلسات المستخدمين الفعلية.
- اختبار رسائل البريد، أو الواجهات المرئية في جميع الأقسام.

**ملاحظة مستقبلية مهمة:** تُظهر `pg_default_acl` وجود منح افتراضي لـ `anon` و`authenticated` على وظائف جديدة ينشئها `postgres` داخل `public`. هذه إعدادات افتراضية للوظائف الجديدة، ولا تغيّرها الترجمات الحالية. يجب التخطيط لتغييرها لاحقًا مع مراجعة جميع `GRANT EXECUTE` في الترحيلات القادمة، لأن الإغلاق الفوري قد يكسر وظائف جديدة تعتمد على المنح التلقائي.

**مرجع رسمي:** https://supabase.com/docs/guides/database/functions

## الاستعادة إذا ظهر خلل

لم تُحذف دوال أو بيانات. يمكن إعادة منح `EXECUTE` للدوال الأربع **فقط عند الحاجة وبعد تحديد السبب**. راجع ملف الترحيل وسجل التغييرات بدل تشغيل منح عامة على كل الدوال. الإصلاح الأول لا يغيّر صلاحيات المحررين المخولين ولا يُحتاج التراجع عنه إذا كانوا يستعملون القناة المعتمدة.
