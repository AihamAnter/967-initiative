# تقرير الهندسة والأمن والأداء — مبادرة 967

تاريخ الفحص: 16 أكتوبر 2026. المسؤول: Software Architecture, Security & Performance Specialist، وكيل مستقل ضمن الفريق. نطاق هذا التقرير هو التغييرات المحلية في فرع `audit/launch-readiness`؛ لم تُنشر هذه التغييرات ولم يُعدّل أي سجل في قاعدة الإنتاج.

## النتيجة وحدودها

تحسّن الأمان البرمجي، وأصبح تدقيق اعتماديات الإنتاج لا يسجل ثغرات معروفة. تبقى خمسة إدخالات عالية الخطورة في سلسلة أدوات ESLint التطويرية مرتبطة بثغرة واحدة في `braces` لا يتوفر لها إصدار مصحح وقت الفحص. ليست هذه نتيجة «صفر ثغرات» لجميع الاعتماديات.

لا يمكن اعتماد تسجيل الدخول، صلاحيات الحسابات الحقيقية، حفظ المحتوى، دعوات البريد، إرسال الرسائل أو رفع الملفات بوصفها مختبرة بالكامل. أكد المستخدم عدم وجود بيئة staging أو حساب تجريبي؛ لذلك لم تُنفذ عمليات مصادقة أو كتابة في قاعدة الإنتاج. اجتياز الاختبارات الوحدوية واختبارات رفض الطلبات لا يعوض اختبار هذه السيناريوهات بحسابات آمنة.

## النطاق والبنية

- Next.js App Router مع React 19، وSupabase للمصادقة وPostgres وStorage، وواجهتي `/api/contact` و`/api/admin/editors`.
- راجعت كود الواجهات الخلفية، حدود الطلبات، الأخطاء، التحقق من الدور، تحميل البيانات العامة، SQL/RLS، رفع الوسائط، متغيرات البيئة، رؤوس HTTP والاعتماديات.
- يظل `SUPABASE_SERVICE_ROLE_KEY` محصوراً في وحدات `server-only` وواجهات الخادم؛ لا يوجد استعمال له في مكونات العميل. ليست مفاتيح `anon` العامة أسراراً؛ خصوصية البيانات تعتمد على grants وRLS. [توثيق Supabase](https://supabase.com/docs/guides/database/postgres/row-level-security).
- تحميل البيانات العام في `lib/data.js` يستخدم service role مع مرشحات نشر صريحة. لم أبدله بصورة عمياء إلى anon لأن فحص الشركة المباشر أظهر `401`؛ يجب تصحيح/اعتماد RLS أولاً ثم دراسة القراءة بأقل صلاحية.
- تقارير قياس Lighthouse والبناء واختبارات المتصفح النهائية يتولاها المدير التقني وتوجد في التقرير الموحد؛ هذا التقرير لا يدّعي قياس تحسن السرعة بمفرده.

## إجراءات الإغلاق المتبقية

1. إنشاء بيئة معزولة وحسابات اختبار بأدوار معروفة، ثم اختبار التسجيل/الدخول والاستعادة والخروج والرفع وCRUD والصلاحيات وأخطاء الشبكة. لا يُستخدم إنتاج حقيقي لهذا الاختبار.
2. مراجعة وتجربة `launch-hardening-proposed.sql` وأخذ snapshot للسياسات الحالية قبل أي تطبيق معتمد. الملف **غير مطبق** وقد يحتاج ملاءمة لسياسات إضافية خارج المستودع؛ permissive policies تتحد بعملية OR.
3. تثبيت Node متوافق في Vercel، والتحقق من متغيرات Supabase ومفتاحي Turnstile وضبط redirects/SMTP وسياسة تسجيل الحسابات ومراقبة الأخطاء وفق إعداد الحساب الفعلي.
4. متابعة إصلاح braces، وتحديد سياسة سرية مرفقات المسودات وحماية spam المشتركة وتواتر تدقيق الاعتماديات.

التقدير الداخلي المقترح للأمان والخصوصية: **5/10 قبل،7/10 بعد**، بوزن واضح لا يُمنح فيه نجاح لاختبارات auth/CRUD غير المنفذة. لا يقدم هذا الوكيل حكماً READY FOR PRODUCTION مع بقاء ENG-14، ولا يختزل جاهزية المنصة في نتيجة npm أو نجاح البناء.
