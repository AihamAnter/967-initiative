# موقع 967 — المرحلة الأولى: ظهور الأقسام والصلاحيات

تاريخ الفحص: 2026-10-31

## النطاق والنتائج
- مراجعة إعدادات ظهور الأقسام وتخطيطات الصفحات وحاجز PublicPageBoundary.
- مراجعة authorizeEditorRequest وصلاحيات RLS ودوال SECURITY DEFINER في Supabase.
- لا تغييرات بصرية، ولا تعديل لبيانات المستخدمين أو نصوص المحتوى.

### 1. خطأ روابط الشخصيات داخل الخريطة
تخطيط app/yemen-map/layout.jsx يحمي الأطلس مسبقًا؛ لذلك لم يُضف له حاجز مكرر. لكن pageIsVisible كان يعد رابط /yemen-map/figures/<slug> ظاهرًا عند إخفاء الأطلس وظهور الشخصيات، رغم أن الصفحة لا تفتح في هذه الحالة. أصبح الرابط يحتاج ظهور الأطلس والشخصيات معًا. دليل الشخصيات المستقل لا يتأثر.

### 2. حماية الصفحات الفرعية
أُضيفت حواجز خادمية للألعاب والتاريخ والشخصيات على مستوى layout حتى تتوارثها الصفحات الفرعية الجديدة. لم تتغير الفحوص الأصلية.
استوديو مدرسة 967 الإداري يبقى منفصلًا عن إخفاء النشر العام، ليتمكن المسؤولون من تجهيز المحتوى؛ حماية البيانات فيه تعتمد على APIs موثوقة وصلاحيات مستخدم.

### 3. صلاحيات محرر لا تراعي حالة الحساب
التحقق في API كان يتطلب تأكيد البريد وعدم الإيقاف، أما ست دوال SQL للترخيص فكانت تعتمد فقط على العضوية في editors. أصبحت is_editor وis_967_editor وis_management وis_ranking_editor وdebate_role وtask_role تستند إلى editorial_can_read القائمة التي تتحقق من الصلاحية وحالة الحساب.
حُفظت تواقيع الدوال وملكية تنفيذها وقائمة المسموح لهم باستدعائها.

### 4. سياسات RLS والأداء
أصلحنا المسار المباشر لقراءة editor_drafts وmessage_followups الذي لم يفحص حالة الإيقاف/التأكيد، ووحدنا استعمال auth.uid وdebate_role بشكل قابل للتخزين المؤقت عبر SELECT فرعي في ثماني سياسات SELECT دون توسيع نطاق الوصول.
حُذف فهرس debate_vote_distribution_idx المكرر، مع إبقاء debate_vote_poll_idx بعد إثبات التطابق وعدم ارتباط أي منهما بقيد.

## ملاحظات Supabase Advisor قبل الإصلاح
- 12 جدولًا لديها RLS دون سياسة؛ قد يكون ذلك مقصودًا لمنع القراءة المباشرة للبيانات الداخلية. لا نفتحها بإضافة سياسة عامة.
- 14 دالة SECURITY DEFINER قابلة للاستدعاء دون تسجيل و42 للمسجلين. بعضها مخصص لاستطلاع بيانات عامة أو مستخدم في RLS؛ سحب صلاحيات التنفيذ جماعيًا قد يكسر ميزات الموقع.
- تنبيه حماية كلمات المرور المسرّبة: إعداد مستقل في Supabase Auth، لم يُغيّر في هذه المرحلة. المرجع: https://supabase.com/docs/guides/auth/password-security#password-strength-and-leaked-password-protection
- 8 تنبيهات auth_rls_initplan وفهرس مكرر واحد: تمت معالجتها في الترحيل.
- 31 مفتاحًا أجنبيًا بلا فهرس، و14 فهرسًا غير مستخدم، و14 تداخلًا بسياسات السماح: تحتاج قياس الاستخدام قبل حذف أو إضافة فهارس وسياسات على نطاق واسع.

## التحقق
اختبارات مستقلة في tests/phase1-authorization-and-visibility.test.mjs تغطي حالات الإدارة والإدارة العليا والمستخدم العادي وغير المؤكد والموقوف والزائر، وحماية المسودات المباشرة وروابط الأقسام. وتستمر الاختبارات العامة من tests/page-visibility.test.mjs وtests/migration-layout.test.mjs.
يجب تشغيل npm test وnpm run lint وnpm run build قبل الدمج، ومطابقة سجل ترحيلات Supabase قبل الدمج النهائي.

إخفاء الأقسام وظيفة نشر عامة وليس حاجزًا أمنيًا بديلًا عن RLS. لم نعدّل إعدادات العرض الحالية للمستخدمين.
