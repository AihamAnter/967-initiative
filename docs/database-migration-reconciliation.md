## لماذا لا نصلح السجل فوراً؟

`migration repair --status applied` يسجّل فقط أن ترحيلاً *سبق أن طُبق*؛ لا ينفذ SQL ولا يتحقق من صحته تلقائياً. تسجيل 19 ملفاً على أنها مطبقة سيكتب تاريخاً غير صحيح.
كذلك فإن استعمال `db push` قبل إصلاح سجل الترحيلات قد يعيد محاولة تشغيل SQL قديم على الإنتاج.

## خطة العمل الآمنة اللازمة لإكمال المهمة

### 1. نسخة احتياطية قابلة للاستعادة (متطلب إيقاف)

أجرِ النسخ من جهاز أو بيئة موثوقة باستخدام Supabase CLI بعد `supabase login` و`supabase link` (التحقق من رابط المشروع قبل الاتصال):

```sh
supabase db dump --linked -f roles.sql --role-only
supabase db dump --linked -f schema.sql
supabase db dump --linked -f data.sql --use-copy --data-only
```

**لا ترفع ملفات `roles.sql` أو `data.sql` إلى GitHub**؛ قد تحتوي معلومات تخص المستخدمين، وتحتاج تخزيناً خاصاً مشفراً. تحقّق من أن الملفات غير فارغة وقابلة للاستعادة على قاعدة *منفصلة*، ولا تخلطها مع ملفات migrations. نسخ قاعدة البيانات لا يشمل ملفات Storage نفسها؛ تحفظ منفصلة إن كانت مطلوبة لاستعادة الموقع بالكامل.

### 2. استخراج Baseline غير مُعدِّل

- استخرج مخطط الإنتاج مباشرة باستخدام `supabase db dump --linked -f baseline_candidate.sql`؛ هذا ليس نفسه تسجيل Migration.
- راجع SQL وRLS والـgrants والـfunctions والـtriggers والـsequences والـextensions، مع الانتباه إلى التعديلات اليدوية في صلاحيات `anon` و`authenticated`.
- راجع أيضاً ملفات SQL المنفردة في جذر `supabase/`، وليس ملفات `migrations/` التسعة عشر فقط.
- لا تجعل `baseline_candidate.sql` ملف Migration رسمياً قبل نجاح الخطوة 3.

### 3. اختبار إعادة البناء

- حافظ على كامل التاريخ القديم بأرشيف مُراجع؛ لا تحذفه أو تدمجه عشوائياً في Baseline. بعض الاختبارات الحالية تقرأ أسماء ملفات migrations مباشرة، ولذلك نقلها يتطلب تحديث الاختبارات.
- في بيئة محلية أو قاعدة اختبار منفصلة، ابدأ من مخطط نظيف، واختبر استعادة Baseline، ثم قارن الفهرس والصلاحيات والسياسات والدوال مع الإنتاج.
- تأكد من إمكانية إجراء migration جديد تجريبي على **قاعدة الاختبار فقط** ثم إعادة الاختبار.

### 4. التسوية الفعلية (بعد اجتياز البوابتين)

- استخدم Supabase CLI `supabase migration new <name>` لإنشاء اسم رسمي لملف Baseline، بدلاً من اختراع اسم مادي.
- راجع طريقة جعل GitHub يحتوي على سلسلة migrations واحدة قابلة لإعادة البناء.
- بعد **التحقق من النسخ الاحتياطي واختبار Baseline**، سجل نسخة Baseline المؤكدة كمطبقة باستعمال `supabase migration repair <version> --status applied` وفق الوثائق، من دون إعادة تشغيل SQL.
- نفذ `supabase migration list` وتحقق من تطابق الحالة المحلية والبعيدة، ومن استمرار عمل الموقع ووظائفه وبياناته.
- لا تُجرِّب `db reset` أو `db push` على قاعدة الإنتاج لمجرد استكشاف الخطأ.
