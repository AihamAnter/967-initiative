# مركز مهام مبادرة 967

المسار الداخلي: `/admin/tasks`. يستخدم جلسة Supabase Auth الحالية وجدول `editors`؛ لا ينشئ حسابات أو نظام دخول جديداً. يظهر رابط المركز وبطاقة الملخص داخل `/admin` للحسابات المعتمدة فقط. صفحات الموقع العامة والبحث وSitemap و`llms.txt` لا تستورد بيانات المهام.

## التثبيت بالترتيب

1. احتفظ بنسخة احتياطية، وجرّب أولاً على مشروع Supabase **اختباري منفصل**. لا تستخدم بيانات أو حسابات الإنتاج للاختبار.
2. يفترض التثبيت وجود `supabase/schema.sql` و`supabase/admin-roles.sql` المطبّقين مسبقاً، بما فيه جدول `editors` وعمود `role`. لا تُعد تشغيل ملف الأدوار تلقائياً؛ يحتوي الملف القديم على ترقية أول حساب عند غياب الإدارة. مركز المهام لا يغير أي دور قائم.
3. راجع `supabase/task-center.sql` ثم نفّذه مرة واحدة في SQL Editor للمشروع الاختباري. الملف مستقل، داخل معاملة `begin/commit`، وينشئ جداول وفهارس وسياسات ودوال جديدة فقط. فشل أي خطوة يُبطل المعاملة. ليس ملفاً قابلاً لإعادة التشغيل فوق تثبيت موجود؛ عند نجاح التطبيق لا تعِد تشغيله، بل استخدم Migration إضافية لأي تغيير لاحق.
4. عيّن متغيري البيئة الموجودين `NEXT_PUBLIC_SUPABASE_URL` و`NEXT_PUBLIC_SUPABASE_ANON_KEY`. لا يحتاج هذا القسم إلى Service Role Key. الأقسام القديمة قد تحتاج `SUPABASE_SERVICE_ROLE_KEY` وفق إعداداتها القائمة؛ لا تغيّرها. لا توجد أسرار جديدة أو خدمة تخزين مطلوبة.
5. شغّل `npm ci` ثم `npm test` و`npm run lint` و`npm run build`.
6. نفّذ تحقق Supabase الاختباري الموضح أدناه. بعد مراجعته وموافقة صاحب المشروع صراحةً يمكن تطبيق SQL نفسه على الإنتاج. **لم يُطبّق الملف على الإنتاج ولم يُنشر الموقع تلقائياً.**

في PowerShell استخدم `npm.cmd` إذا كانت سياسة الجهاز تمنع تشغيل `npm.ps1`.

## الاستخدام

- استخدم «إضافة مهمة» لإدخال العنوان والوصف والمشروع والمسؤول والأولوية والحالة والمواعيد والوقت المقدّر والوسوم والروابط والملاحظات وخيار اعتماد الإدارة والتكرار. يُثبّت مسؤول المهمة على المستخدم نفسه لدى الأدمن.
- كل أعضاء الإدارة والأدمن يرون **جميع** مهام الفريق، ويستطيعون البحث فيها والتعليق عليها. «مهامي» فلتر اختياري وليس قيد وصول.
- الفلاتر والبحث والترتيب والعرض والأرشيف والصفحة تُحفظ في URL. نافذة التفاصيل لا تستبدل الصفحة. يمكن مشاركة رابط يحمل `task=<uuid>` مع عضو مخوّل.
- القائمة تُقسّم إلى صفحات من 30 مهمة. Kanban يعرض مهام الصفحة نفسها مع ستة أعمدة، ويتيح السحب على الكمبيوتر وقائمة حالة على كل بطاقة للهاتف ولوحة المفاتيح. تُحفظ الحركة قبل تحديث موقع البطاقة؛ الفشل يبقي الحالة المحفوظة مع رسالة واضحة.
- التقويم شهري أو أسبوعي؛ اضغط يوماً لعرض مهامه، واستخدم أزرار الفترة السابقة/القادمة و«اليوم». يظهر لكل يوم العدد وإشارات المستحقة والمكتملة والمتأخرة. حد الصفحة 300 مهمة داخل الفترة؛ عند تجاوزها يظهر التنقل بين الصفحات.
- داخل التفاصيل: إكمال أو إرسال للمراجعة، تعديل، خطوات مع ترتيب ونسبة محسوبة، روابط، مناقشة، وسجل نشاط بالقيم السابقة والجديدة. لا تظهر نسبة خطوات تقديرية عند غياب الخطوات.
- تعديل التعليقات وحذفها متاحان لكاتبها وللإدارة. يظهر وقت تعديل التعليق ويبقى أثر التعديل أو الحذف في السجل.
- يمكن أرشفة المهمة المكتملة، ومشاهدة الأرشيف واستعادتها. استعادة المهمة لا تعيد فتحها تلقائياً. إعادة فتحها تحولها إلى قيد التنفيذ وتحفظ سجل الإكمال السابق.
- حذف المهمة من مساحة العمل متاح للإدارة فقط بعد تأكيد. هذا **حذف منطقي نهائي من الواجهة** عبر `deleted_at`؛ لا تُحذف البيانات الفعلية أو سجل التدقيق. لا توجد أداة استعادة المحذوف من الواجهة.
- إدارة المشاريع تتيح إنشاء تصنيف أو تغيير اسمه أو إيقافه وتفعيله، دون إزالة المهام المرتبطة به. التصنيفات الافتراضية الأربعة عشر بيانات إعداد تنظيمية وليست مهام تجريبية أو مشاريع منشورة.

## الوقت والتقارير

- الموعد ذو الساعة يُدخل بتوقيت جهاز المستخدم، ويُحفظ `timestamptz` ويُعرض محلياً. يُرفض الوقت المحلي غير الموجود أثناء الانتقال إلى التوقيت الصيفي.
- الموعد بلا ساعة يُحفظ `due_date` مع منطقة IANA في `due_timezone`. ينتهي في **منتصف الليل التالي حصراً** في تلك المنطقة. لا تُختلق ساعة تسليم. الإكمال عند هذا الحد أو بعده متأخر. لا يمكن وجود `due_at` و`due_date` معاً.
- التأخر وصف محسوب من الموعد والوقت الفعلي، وليس حالة مهمة. الملغاة والمكتملة والمؤرشفة والمحذوفة لا تُعد متأخرة حالياً.
- لوحة الأداء تُحسب للفريق كاملاً؛ الفلاتر تغيّر النتائج فقط. الأرشيف والمحذوف مستبعدان. معدل الإنجاز = المكتملة ÷ النشطة غير الملغاة. الالتزام = المكتملة في موعدها ÷ المكتملة التي لها موعد؛ يظهر «—» عند غياب المقام.
- «خلال ٧ أيام» يشمل اليوم والأيام الستة التالية حسب التاريخ المحلي.
- التقرير الأسبوعي من الإثنين 00:00 في منطقة المستخدم حتى الآن. الإنشاء والإكمال بحسب التواريخ الفعلية. إعادة الفتح تستبعد المهمة من المكتمل حالياً، مع بقاء الحدث التاريخي في السجل. توزيع الأسبوع يشمل المهام التي أُنشئت أو اكتملت خلال الأسبوع، مرة واحدة لكل مهمة. المتأخر حالياً يشمل التراكم السابق أيضاً.
- تصل تحديثات الساعة عند فتح المركز وتحديثه، وكل دقيقة أثناء ظهور الصفحة. الحفظ يحدث الواجهة فور تأكيده.

## التكرار والتنبيهات والمرفقات

**التكرار عند الإكمال:** تنشأ نسخة تالية واحدة داخل معاملة الإكمال نفسها، مع نسخ الوصف والوسوم والروابط والموعد والخطوات، وإعادة الحالة والخطوات إلى البداية. المفتاح الفريد `recurrence_of` يمنع ازدواج النسخة، وقفل الصف و`revision` يمنعان حفظ طلبين بالنسخة القديمة. إعادة فتح المهمة وإكمالها لا تولّد نسخة أخرى. تغيير جدول التكرار لا يغير نسخة سبق إنشاؤها.

الزيادة اليومية/الأسبوعية/الشهرية تتبع الوقت المحلي في المنطقة المخزنة، وتحافظ على الساعة عبر تغيير التوقيت الصيفي. الشهر يُقصر إلى آخر يوم صالح؛ مثال 31 يناير ← 28 فبراير ← 28 مارس. لا تُنشأ نسخ للأيام الفائتة تلقائياً؛ نسخة واحدة لكل إكمال. الموعد المتأخر قد ينتج موعداً تالياً ما زال متأخراً، حتى يعالج الفريق التراكم. المهمة الدورية بلا موعد تبقى نسختها التالية بلا موعد. إيقاف المشروع لا يمنع نسخ مهامه القائمة.

**التنبيهات:** الإسناد وطلب الاعتماد وإعادة الفتح والتعليق تنشئ سجلات فور الحدث. تنبيهات الموعد القادم خلال 24 ساعة والتأخر تُنشأ للمستخدم المسؤول عند فتح المركز؛ مفتاح يتضمن نوع التنبيه والموعد والمنطقة يمنع التكرار. قراءة التنبيه شخصية، مع تحديد واحد أو الجميع كمقروء. تعرض النافذة آخر 100 تنبيه.

**لا يوجد Cron أو إرسال بريد أو تنبيه خارج الموقع في هذا الإصدار.** هذه الآلية لا تتطلب إعداد Vercel Cron. إذا طُلب تذكير أثناء إغلاق الموقع لاحقاً، يلزم مسار خادم مجدول منفصل محمي بسر، وجدولة Vercel واختبارها قبل وصفها بأنها مفعّلة؛ لا يوجد مسار عام غير محمي حالياً.

الروابط المرجعية مدعومة بالكامل حتى 20 رابط HTTP/HTTPS لكل مهمة، دون بيانات اعتماد في الرابط. تُفتح مع `noopener noreferrer`، وصفحة المركز تستخدم `no-referrer`. **رفع الملفات غير مفعّل**؛ يتطلب Bucket خاصاً وسياسات Storage وروابط موقعة وأحجاماً وأنواعاً مسموحة في إعداد منفصل. لا يُستخدم Bucket `media` العام لملفات المهام.

## الجداول والصلاحيات

| الجدول | الغرض | القراءة | الكتابة |
|---|---|---|---|
| `tasks` | المهام والمواعيد والمراجعة والتكرار والأرشفة | كل الأدمن والإدارة | المسؤول عن المهمة أو الإدارة؛ الإسناد والحذف والموافقة للإدارة |
| `task_projects` | تصنيفات داخلية | كل الفريق المعتمد | الإدارة فقط |
| `task_subtasks` | خطوات مرتبة وتواريخ إكمال | كل الفريق المعتمد | من يحق له تعديل المهمة |
| `task_comments` | المناقشات ووسم التعديل | كل الفريق المعتمد | إضافة للجميع؛ التعديل والحذف للكاتب أو الإدارة |
| `task_activity` | سجل دائم بالقيم والفاعل والوقت | كل الفريق المعتمد، بما فيه أثر المحذوف | Triggers فقط؛ لا تعديل أو حذف من التطبيق |
| `task_notifications` | أحداث وتنبيهات شخصية | المستلم المعتمد فقط | Triggers وتذكيرات مضبوطة؛ المستلم يعدل `read_at` فقط |

كل الجداول مفعّل عليها RLS. لا يملك `anon` امتيازات الجداول أو الدوال، والمستخدم غير الموجود في `editors` لا يرى صفوفاً ولا يستطيع تنفيذ العمليات. الربط بـ`auth.users` لا ينشئ جدول مستخدمين موازياً؛ دالة `task_team()` تعرض المعرّف والاسم والدور فقط للأعضاء المخولين دون البريد أو بيانات Auth الخاصة. لا تُعدّل سياسة `editors` الحالية لتوسيع القراءة.

الخادم يتحقق من Bearer والجلسة والدور وOrigin قبل القراءة أو التحوير. يستخدم عميل Supabase بامتياز المستخدم ومفتاح anon، حتى تبقى RLS مطبقة خلف API. حقول النظام ليست قابلة للكتابة بامتيازات `authenticated`، وTriggers تتولى أوقات الإكمال والفاعل والنسخة والتدقيق. دوال `security definer` ضيقة النطاق تثبّت `search_path=''` وتتحقق من `auth.uid()` والدور؛ الدوال الداخلية مسحوب منها التنفيذ العام.

`task_mutate` تعمل بامتيازات المستدعي وتستخدم RLS. مساعد القفل المصرح للفريق يسمح بتسلسل التعليقات على مهام الآخرين دون منح حق تعديلها. مساعد الحذف المنطقي يتحقق من الإدارة والنسخة، لأن جعل الصف محذوفاً يخرجه من سياسة القراءة. كل التغييرات داخل معاملة PostgreSQL واحدة، والأخطاء تمنع الحفظ الجزئي.

مراجع التصميم الأمني: [Supabase RLS](https://supabase.com/docs/guides/database/postgres/row-level-security)، [Database functions](https://supabase.com/docs/guides/database/functions)، [Next.js route handlers](https://nextjs.org/docs/app/getting-started/route-handlers).

## تشغيل الاختبارات وإعادة التحقق

`npm test` يشغل المنطق وAPI وجداول SQL الفعلية داخل PostgreSQL معزول من خلال PGlite، بهويات Admin A وAdmin B وManagement C وزائر ومستخدم غير معتمد. الـAuth المستخدم في المعزل بديل محلي، وليس خدمة Supabase Auth الإنتاجية.

لاختبارات الواجهة يلزم Playwright وAxe (موجودان في أدوات تدقيق هذا المشروع). إن لم يتوفرا:

```powershell
npm.cmd install --prefix .audit-tools --no-save playwright @axe-core/playwright
```

ثبّت Chromium عبر Playwright أو حدّد `AUDIT_CHROME_PATH` لمساره. شغّل خادم التطوير المعزول في نافذة طرفية:

```powershell
$env:NEXT_TASK_PREVIEW='1'
$env:NEXT_PUBLIC_SUPABASE_URL='http://127.0.0.1:54321'
$env:NEXT_PUBLIC_SUPABASE_ANON_KEY='task-local-test'
$env:SUPABASE_SERVICE_ROLE_KEY=''
node node_modules/next/dist/bin/next dev --hostname 127.0.0.1 --port 3104
```

ثم `node scripts/test-task-browser.mjs`. الاختبار يعترض كل طلب بيانات مهام في المتصفح ويستدعي معالج API الفعلي على PostgreSQL المعزول؛ لا يرسل طلبات اختبار إلى Supabase الإنتاجي. المقاسات: 320، 390، 768، 1440، 1920. يمكن تغيير `CHECK_BASE_URL` إلى خادم loopback آخر فقط. أوقف الخادم عند الانتهاء. لا تستعمل معرّفات أو رموز جلسات الاختبار في بيئة منشورة.

## تحقق Supabase الاختباري قبل الإنتاج

بعد تطبيق SQL على مشروع اختبار منفصل، أنشئ ثلاثة حسابات Auth اختبارية وامنحها `admin` و`admin` و`management` في `editors` بمعرفة صاحب المشروع. تحقّق عبر المتصفح وكذلك REST مباشرة بمفتاح anon وBearer لكل حساب:

1. كل الثلاثة يقرؤون مهام الآخرين وتفاصيلهم والتعليقات والسجل، و`task_team()` لا يعرض أي بريد.
2. الأدمن ينشئ لنفسه فقط، ويعدل أو يكمل مهامه المسندة إليه. محاولة تعديل مهمة غيره أو إعادة إسنادها تفشل، وكذلك تعديل الأدوار أو حقول النظام.
3. الإدارة تسند إلى أدمن وتعدل مهمة غيرها، وتعتمد المراجعة، وتؤرشف وتستعيد وتحذف من مساحة العمل. الحساب غير المعتمد لا يصح مسؤولاً جديداً.
4. الأدمن يستطيع التعليق على مهمة زميل؛ لا يستطيع تعديل تعليق الزميل، بينما الإدارة تستطيع وتظهر علامة التعديل.
5. دون جلسة: API يعيد 401 ولا تعرض REST بيانات. مع حساب غير معتمد: API يعيد 403 ولا تعرض REST صفوف المهام أو المشاريع أو السجل.
6. أرسل إكمالين بنفس `revision` من جلستين متزامنتين حقيقيتين: ينجح واحد ويرفض الآخر كتعارض. توجد نسخة دورية تالية واحدة فقط. كرر بعد إعادة الفتح: لا توجد نسخة إضافية. تحقّق أيضاً من تغيّر مسؤول المهمة بالتزامن مع التعديل.
7. حاول `UPDATE/DELETE/INSERT` مباشرة على سجل النشاط، وتغيير `user_id` لتنبيه، وتعيين `completed_by` يدوياً؛ تُرفض العمليات.
8. جرّب الموعد الكامل عند حد منتصف الليل والمنطقة المختلفة، وموعد الساعة حول تغيير التوقيت الصيفي، وراجع `completed_at` و`completed_by` وسجل الإكمال.
9. تحقق من `noindex,nofollow` و`Cache-Control: private,no-store` ومن غياب أسماء المهام من HTML العام وSitemap والبحث و`llms.txt`.

محدودية الاختبارات المحلية: PGlite محرك PostgreSQL فعلي، لكنه يستخدم اتصالاً واحداً؛ الطلبات المتنافسة المحلية تختبر القفل وCAS والتفرّد في المحرك، ولا تثبت كل سلوك الشبكة أو العزل متعدد الاتصالات في Supabase/PostgREST. يلزم فحص بيئة الاختبار أعلاه قبل اعتماد جاهزية الإنتاج. كذلك حساب المؤشرات يجمع الصفوف على الخادم على دفعات ثم يرسل صفحة النتائج فقط؛ عند نمو حجم الفريق والبيانات كثيراً يستحسن نقل التجميع والبحث إلى SQL لتحسين زمن القراءة.
